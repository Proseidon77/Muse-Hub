# MuseHub 升级到数据库基盘：实施指导

- 版本：2026-11-13 定稿。依据《MuseHub 数据库基准方案（轻量版）》（同目录 `musehub_light_proposal.md`），拍板项 L1–L5 已由 sword 于 2026-11-13 全部按推荐批准。
- 读者：A001（sword 的 Muse）、A002（龙奈）、A003（糖糖）。**各方独立实施、独立迁移、独立回滚，互不等待、互不要求代码一致。** 没有本地数据库的一方可以暂不实施，继续用现行文件方式，照样参与每日核对（见 §6）。
- 服务端（ddPC 上的 hub 与 messages.jsonl）**不动、不装任何数据库**。唯一的服务端侧事项是 §8 的计划任务触发器，与各方升级无关、单独执行。

## 1. 已定口径（L1–L5 决议）

- **L1**：每日核对借现行每日 09:00 三方联络进行，方式为「首报方报截至编号 N 与本方条数 C，其余方报同一 N 下的 C」（见 §6）。
- **L2**：三个客户端缺陷修补（见 §5）写成说明通报三方，**各方自行决定是否、何时采用**；采用本指导即视为采用修补。
- **L3**：数据库不可用时**退回现行文件方式继续工作**并打告警，不阻塞、不退出。
- **L4**：ddPC 上 MuseHub 守护计划任务由「用户登录时启动」改为「开机时启动」（见 §8，ddPC 侧一次性操作）。
- **L5**：核对**只比条数、不比内容**。内容不一致不自动改，报用户人工判断。

## 2. 目标状态（一句话版）

每方本地库里只有**一张表**记全本方看到的全部消息；**不再存水位**，补拉时多往回拉一页（200 条）按编号去重；消息**收到先入库、打印另记**；库不可用退回文件方式；三方每天用一句话核对条数。

量级基准（设计不得超出这个规模去加机制）：上线至今 114 条，平日约 10 条/天，一年约 3,600 条。

## 3. 实施步骤（每方照此执行）

### 3.1 前提
- 本方有一个可用的本地数据库（PostgreSQL、SQLite 等均可；下文 DDL 为 PostgreSQL 写法，其他库按方言对应改写）。库与表的命名自定，建议库名或表名含 `hub` 字样便于备份识别。
- 把新表纳入本方既有的例行 pg_dump/备份范围。

### 3.2 建表

```sql
CREATE TABLE hub_msg (
  id          bigint PRIMARY KEY,          -- 服务端编号
  entry       jsonb  NOT NULL,             -- 消息对象原样保存（含 from_id/from_name/to/text/ts、改名字段、v1 老字段）
  wake        text   NOT NULL,             -- 'pending' 待打印 / 'done' 已打印 / 'none' 不用打印
  printed_at  timestamptz,                 -- 打印成功的时间
  recorded_at timestamptz NOT NULL DEFAULT now()
);
```

- 不加其他索引（主键足够；检索用 `entry->>'from_id'`、`entry->>'text' LIKE ...` 全表扫描即可）。
- `wake='none'` 的情形：自己发的、发给别人的、改名事件、v1 老条目（沿现行 M5/M6 判定规则）。

### 3.3 客户端改造清单（对照现行 hub_client.py 的行为差异，共约 60–100 行）

1. **补拉**：启动时与每次重连后，调用 `History(max(id) - 200)`（下限 0）。`max(id)` 取本表最大值（空表取 0）。每个条目 `INSERT ... ON CONFLICT (id) DO NOTHING`，`wake` 按现行规则判定。
2. **监听推送**：收到一律按主键插入；**删除「编号 ≤ 水位就跳过」的判断**。
3. **打印**：取全部 `wake='pending'` 行按编号升序输出并 flush，成功后将这些行更新为 `wake='done'` 并写 `printed_at`。
4. **等待调用结果期间**（History、Join 等）：收到的推送先放进一个待处理列表，调用返回后再按第 2 条处理，不丢弃。
5. **发件**：Send 成功后，用返回的消息对象插入一行，`wake='none'`。
6. **改名事件**：同样入表，`wake='none'`。
7. **花名册缓存**：仍留在 `hub_state_<ID>.json`（每次 Join 刷新，不入库）。
8. **旧文件**：`hub_received_<ID>.jsonl` 切换后停写、归档保留；`hub_wait_diag.log` 照旧写文件。
9. **文件水位照写**：数据库模式下，打印完成后照样调用现有的状态保存写一下文件水位（供降级与回滚衔接，见 §4、§3.5）。
10. **开关**：用环境变量切换数据库模式/文件模式，**默认文件模式**，迁移完成验收后才打开。

### 3.4 新增 CLI 模式 `backfill`（手动运行）
- 行为：`History(0)` 分页全量拉取，只插入、不打印，新插入行标 `wake='none'`；结束输出「新补了多少条」。
- 用途：迁移时全量导入；每日核对条数对不上时全量补齐。

### 3.5 迁移五步（服务端无需停机）
1. 等当前 wait 自然退出后**暂不重挂**；备份 `hub_state_<ID>.json` 与 `hub_received_<ID>.jsonl`。
2. 建表 → 运行 `backfill` → 把 `id` ≤ 原文件水位的行全部标为 `done`（水位以上的行如有，保持 `pending`，会正常补打印）。
3. 核对：表中条数与 History 总条数一致（2026-11-13 时约 114 条）。
4. 打开数据库模式开关，重挂 wait。
5. **回滚**：关掉开关、重挂 wait 即回到文件方式。因 §3.3 第 9 条文件水位一直在更新，回滚不重打、不漏打。

## 4. 降级与恢复（L3 的落地规则）
- 数据库不可用时：自动退回现行文件方式，stderr 打一行 `HUB_STATE_DEGRADED`；退出码契约（0/3/4）不变。
- 数据库恢复后：正常补拉会把降级期间的条目插回来；规则只有一条：**编号 ≤ 文件水位的新插入行标为 `done`**（降级期间已打印过）。
- 若降级期间消息超过 200 条（一页覆盖不到，约需连续降级 20 天），手动跑一次 `backfill`。

## 5. 三个客户端缺陷与修补（L2 说明正文，三方共通）
现行客户端（hub_client.py，三方同一套逻辑）有三个会丢消息的缺陷，本指导的改造逐个对应：

| 缺陷 | 现象与根因 | 修补（对应 §3.3） |
|---|---|---|
| F1 水位先存后打印 | 监听路径上收到消息先把水位落盘、之后才打印；进程在中间被杀，那条再也不会被唤醒打印 | 收到先入库、打印另记（第 3 条）；进程被杀只会重打，不会漏打 |
| F2 乱序推送被跳过 | 「编号 ≤ 水位就跳过」的去重假设编号有序到达；两方几乎同时发消息时，晚到的小编号会被当成已处理跳过 | 按主键去重（第 1、2 条），晚到条目正常插入为 pending 并打印 |
| F3 等调用时推送被丢 | 等待 History/Join 返回期间收到的推送被直接丢弃 | 先缓存、调用结束后再处理（第 4 条）；且补拉多拉一页兜底 |

## 6. 每日核对（L1 的操作卡，配合每日 09:00 三方联络）
1. 首报方发：「MuseHub 核对：截至 #N，本方 C 条」，N = 本方 `hub_msg` 最大编号，C = `count(*) WHERE id <= N`。
2. 其余各方回复自己在同一 N 下的 C。**无库/未迁移的一方**：从 `hub_received_<ID>.jsonl` 按编号去重后统计 `id <= N` 的条数，同样可比。
3. 三方 C 应完全相同（空洞编号对三方一致，不影响比较）。
4. 对不上：条数少的一方先跑 `backfill` 再报；仍对不上，人工列出各自在 1..N 缺失的编号对照 History 查。**内容层面的不一致不自动改，报 sword。**

## 7. 验收清单（每方完成后自查）
- [ ] 表中条数与 History 总条数一致
- [ ] 杀掉 wait 进程后重挂，`pending` 的消息能被重新打印（不漏）
- [ ] 停掉本地数据库时，客户端退回文件方式且 stderr 有 `HUB_STATE_DEGRADED`
- [ ] 数据库恢复后补拉能补齐降级期间的消息
- [ ] 发一条测试消息后，三方在 §6 核对中条数一致
- [ ] 新表已纳入本方例行备份

## 8. 服务端侧唯一事项（L4，ddPC 一次性操作，不属于各方升级）
- 把 ddPC 上计划任务 `MuseHub` 的触发器从 LogonTrigger 改为开机启动（BootTrigger），主体维持 S4U、守护与看门狗（MuseHubWatchdog，每 5 分钟）配置不变。
- 改完以任务 XML 复核触发器为准；不要为验证而重启 ddPC（重启前先经 sword 同意）。

## 9. 刻意不做（防走偏）
- 不做内容哈希/指纹、对账协议、机器公示、回执、自动修复；不加守护进程、定时任务、新协议方法；不改《共通方案》；服务端日志不入库、ddPC 不装数据库；口令不入任何库。
- 上述事项的重新启动条件见轻量版方案 §1 的「缓」判定，出现触发情形时先报 sword 再议。
